## A.2 GitHub 数据可信化——根因与实现细节（补充 Phase 4 第 4 节）

**已确认根因（2026-05-26 修复前）：**

- `lib/project-update-signals.ts` 在 AI evidence 阶段曾 **insert 一条 `GithubRepoSnapshot`，并将 `forks` / `watchers` / `openIssues` 硬编码为 0**（仅 `stars` 来自 evidence）。
- 导入与批量发布链路此前 **未** 调用完整 GitHub REST 刷新，导致项目页长期显示 0。

**当前实现要点：**

| 项 | 说明 |
|----|------|
| 核心函数 | `refreshProjectGithubFacts(projectId)`（`lib/github-sync.ts`，并从 `lib/github.ts` 再导出） |
| 读取优先级 | 项目页读 `GithubRepoSnapshot` 最新一条（`fetchedAt desc`），**不**用 queue meta 旧值 |
| 失败策略 | API 失败 **不 insert 快照、不用 0 覆盖**；错误写入 `Project.aiSignals.github.lastFetchError` 与 `lastFetchAt` |
| contributors | DB 字段为 `contributorsCount`；API 未返回时保留上一条快照值 |
| 接入点 | `import-json-queue-item.ts`（导入后）、`post-import-project-ai.ts`（source enrichment 后）、`bulk-action/route.ts`（发布前） |
| 批量修复 | `ONLY_ZERO=1 pnpm github:refresh` — 仅处理无快照或 forks/watchers/openIssues **均为 0** 的项目 |

**实库验证（2026-05-26）：** 项目 `danielskry/awesome-rag` 刷新后：`forks=132`，`watchers=16`，`openIssues=52`（均非 0）。

**验证命令：** `pnpm typecheck`、`pnpm build`、`git diff --check` 均已通过。

## A.3 AI 中文化——实现文件补充（补充 Phase 4 第 5 节）

# 附录 C：Phase 4.4 计划细化（2026-05-26 更新，在原文第五节基础上展开）

> 目标不变：Freshness & Activity System。以下按 **当前已有能力** 拆任务，避免重复建设。

## C.1 短期（1–2 周，不改公开页结构）

1. **存量数据修复**
   - 运行：`ONLY_ZERO=1 pnpm github:refresh`（可配合 `QUERY=` 分批）
   - 验收：抽样 GitHub 来源项目 forks/watchers/issues 非异常 0
2. **freshness 可读化（可先不落库）**
   - 运营脚本输出：距 `GithubRepoSnapshot.fetchedAt` 天数、`aiSignals.github.lastFetchError`
   - 后台项目列表增加「仓库数据陈旧」标记（仅 admin，不动公开页）
3. **scheduler 草案**
   - 合并 `pnpm ai:update`（变更检测）与 `pnpm github:refresh`（全量指标）
   - 规则：PUBLISHED + 有 githubUrl → 优先队列；ONLY_ZERO / QUERY 作夜间批处理

## C.2 中期（Phase 4.4 核心）

| 模块 | 内容 |
|------|------|
| Freshness 字段 | `githubLastRefreshedAt`、`staleDays`（或统一 derived from snapshot） |
| Activity 分数 | `githubActivityScore`：stars 增量、commit、issue、release 加权 |
| Priority 队列 | trendingScore 驱动 refresh 频率（热：小时级；冷：周级） |
| Cron | `api/cron/*` 或 `scripts/cron_all.ts` 接入 priority refresh |

## C.3 与中长期方向的对齐（原文第六、七、八节不变）

- 仍坚持 **observer / organizer / tracker**，优先数据质量与动态能力。
- Phase 4.4 完成前，**不建议** 启动推荐算法、排名、商业化大功能。
- Phase 4.5 候选：**项目关系网络**（相似/替代/生态），依赖 4.4 freshness 与可信 snapshot 稳定后再做。

## 2026-05-31 补充：发布 readiness / publish gating 原则调整

本次修复统一了 MUHUB 项目发布链路中的 readiness / publish gating 语义。产品原则已归档到 `docs/product/muhub-product-principles.md`，小节为“发布原则：最小可展示优先，AI增强不阻断发布”。

### 发布控制点

- `lib/project-publishing.ts`
  - `resolveProjectAiPublishQuality`
  - `evaluateProjectPublishReadiness`
  - `buildPublishProjectUpdateData`
  - `publishProjectAfterAiEnrichment`
- `app/api/admin/projects/bulk-action/route.ts`
  - `/admin/projects` 批量发布 API。
- `app/admin/projects/projects-admin-table.tsx`
  - 批量发布 UI 结果提示。
- `app/api/admin/projects/[id]/ai-insight/route.ts`
  - 编辑页手工生成 AI 认知卡后的保存与发布质量字段同步。
- `lib/admin-project-edit.ts`
  - 单项目编辑/发布的基础校验。
- `app/admin/projects/[id]/edit/actions.ts`
  - 后台编辑页保存/发布。
- `app/dashboard/projects/[slug]/actions.ts`
  - 用户侧项目发布。
- `lib/discovery/post-import-project-ai.ts`
  - 导入后 source enrichment、AI insight、AI content、apply fields、auto publish。

### 原阻断字段

修复前，以下非核心增强状态会阻断批量发布或自动发布：

- `aiInsightStatus !== "success"`。
- `aiContentStatus !== "success"`。
- 必须同时具备 `tagline` 和 `description`。
- 必须存在公开来源链接、官网或 GitHub。
- 导入后链路还会因 `aiContentStatus`、`simpleSummary`、`primaryCategory`、`tags` 不完整阻断后续发布。

其中 `aiContentStatus`、GitHub facts refresh、source enrichment、外部来源补全属于质量增强，不应作为发布硬门槛。

### 新发布条件

发布硬门槛调整为最小可展示：

- 项目名存在。
- slug 合法。
- status / visibility 可发布。
- `tagline` 或 `description` 至少一个可展示。
- 有可用 AI 结构化分析 / AI 认知卡内容。

以下内容不再作为 blocked reason：

- AI增强版内容。
- AI传播草稿。
- GitHub facts refresh。
- source enrichment。
- 外部来源补全。
- `full_ai` 状态。
- GitHub URL 是否存在。

批量发布返回结果应区分：

- `blocked`：真正阻止发布的基础条件问题。
- `warnings`：不影响发布的质量问题，例如 AI增强失败、来源增强失败、GitHub refresh 失败。
- `skipped`：不参与本次动作的项目，例如非 DRAFT 项目或不存在的记录。

### GitHub 信息源调整

GitHub 不再是项目信息源强绑定条件：

- 有 GitHub 时使用 GitHub 增强。
- 无 GitHub 时基于 website / sources / article / description 增强。
- 都不足时跳过增强，但不阻止发布。
